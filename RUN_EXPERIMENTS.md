# Новые эксперименты для статьи

Код подготовлен, **автором изменений не запускался**: ни модели, ни тесты, ни анализ,
ни Streamlit. Численных результатов новой серии пока нет. Старые JSON и статья
сохранены; переписывать статью по новым данным будем после ваших запусков.

Все команды ниже выполняйте из **`LLM_Lab_2`**. Приведённые команды рассчитаны
на bash/zsh в Linux или macOS. Для продолжения исследования именно GTX 1650
с 4 ГБ запускайте на исходном компьютере с этой видеокартой. Запуск на Mac
допустим, но это будет другой аппаратный стенд и другое исследование.

## 1. Подготовка

```bash
cd LLM_Lab_2
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
ollama pull llama3.2:3b
ollama pull qwen2.5:3b
```

Нужны Python 3.10+ и Ollama. На Linux проверьте `nvidia-smi`.
Если сервер Ollama ещё не запущен, в **отдельном терминале**:

```bash
OLLAMA_NUM_PARALLEL=1 OLLAMA_MAX_LOADED_MODELS=1 ollama serve
```

Если Ollama уже работает как служба, не запускайте второй сервер: установите эти
параметры в окружении существующей службы и перезапустите её до экспериментов.
Не обновляйте модели, Ollama и зависимости между сериями. Остановите сторонние
генерации, закройте игры и приложения с нагрузкой на GPU. Выполняйте серии по очереди.

Проверка окружения и тегов (без генерации):

```bash
ollama ps
python research.py preflight --out preflight.json
```

В `preflight.json` должны быть обе модели, их digest и реальное квантование.
Основной запуск требует `Q4_K_M`; если ваши теги содержат другие веса, сначала
выберите подходящие теги и явно передавайте их через `--models` во всех командах.
Не переименовывайте сведения о квантовании вручную. Полное размещение в VRAM
не предполагается автоматически: сохраняются `/api/ps`, `size_vram` и GPU-телеметрия.

## 2. Сначала локальные тесты и короткий пробный запуск

```bash
python -m unittest discover -s tests -v
python research.py run --suite smoke --out runs/smoke --repeats 1 --temperatures 0
python research.py analyze --run runs/smoke
```

Smoke — 4 измеряемых запроса: 2 задачи × 2 модели. Откройте
`runs/smoke/analysis/REPORT.md`, `responses.csv` и `summary.json`.
Должно быть 4/4 успешных запросов. Если тесты или smoke завершаются ошибкой,
пришлите вывод терминала и `raw.jsonl`; длинные серии пока не запускайте.

## 3. Основной эксперимент качества — обязательно

```bash
python research.py run --suite quality --out runs/quality --repeats 3 --temperatures 0 0.7 --context 2048 --budget 384
```

Это **360 измеряемых запросов**: 30 заданий × 2 модели × 2 температуры × 3 повтора.
10 категорий, по 3 задания: факты, суммаризация, перевод, логика, извлечение,
Python-код, операционные системы, JSON, объяснения и алгоритмы.
Эталоны не передаются сравниваемым моделям. Одинаковые seed и настройки
используются у обеих моделей. Порядок блоков моделей меняется между повторами;
задачи внутри блока перемешаны. При температуре 0 повторы проверяют устойчивость,
но не превращают один вопрос в несколько независимых задач.

Сохраняются `temperature`, `seed`, `num_ctx`, `num_predict`, `top_p`, `top_k`
и `repeat_penalty`. Ограничение 384 — максимум, а не гарантированная длина ответа.
Ответы, остановленные лимитом (`done_reason=length`), отмечаются отдельно.

### Функциональная проверка кода

Чтобы проверять сгенерированные функции, нужен работающий Docker с Linux-контейнерами.
Один раз загрузите образ:

```bash
docker pull python:3.11-slim
```

Затем запустите анализ всей серии:

```bash
python research.py analyze --run runs/quality --execute-code
```

Выполнение кода происходит в одноразовом контейнере без сети и без доступа
к папке проекта, с ограничениями ресурсов. Сам анализ моделей повторно не вызывает.
Функции проверяются на пустых строках/массивах, граничных случаях и отрицательных
примерах; оформление «только код» оценивается отдельно.

Если Docker отсутствует, доступен анализ без выполнения функций:

```bash
python research.py analyze --run runs/quality
```

Тогда задачи кода **полностью исключаются из общего task success**, а не считаются
успешными по наличию похожего кода. Укажите мне, что функциональной проверки не было.
Повторить анализ с `--execute-code` позднее можно без повторной генерации ответов.

## 4. Скорость при разной длине входа и бюджета ответа — обязательно

```bash
python research.py run --suite speed --out runs/speed --repeats 5 --contexts 2048 4096 --input-repetitions 1 8 24 --budgets 64 256
python research.py analyze --run runs/speed
```

Это **120 измеряемых запросов**: 2 модели × 2 контекста × 3 длины входа ×
2 выходных лимита × 5 повторов. Входы задаются количеством одинаковых предложений;
на графике используется фактический `prompt_eval_count`, а не заявленное число
«входных токенов». Выходы могут завершаться раньше лимита: сравнивайте фактические
`eval_count` и `done_reason`. Это sweep лимитов, а не эксперимент с принудительно
одинаковой длиной выходов.

Контекст 4096 может увеличить расход VRAM и вызвать частичную выгрузку на CPU
или ошибку. Такие результаты важны: они сохраняются и не заменяются выдуманными
значениями. Если серия завершается с ошибками, сохраните `raw.jsonl` и телеметрию.
Не смешивайте CPU/offload и полное размещение в VRAM в один вывод о скорости.

Для основной таблицы скорости используйте **`speed_by_condition.csv`**:
там отдельная строка на каждую комбинацию модели, контекста, входа и лимита.
Сводное время по всем разным входам не является честным рейтингом быстродействия.
При пяти повторах p95 — лишь описательный показатель малой выборки.

## 5. Холодный запуск — обязательно

```bash
python research.py run --suite cold --out runs/cold --repeats 5 --context 2048
python research.py analyze --run runs/cold
```

Это **10 измеряемых запросов**: 2 модели × 5 повторов. Перед каждым запросом
модель выгружается из Ollama; прогрев не выполняется. `load_sec` показывает
серверную загрузку, TTFT — клиентскую задержку. Это холодный запуск модели,
**не очистка дискового кэша ОС**. В quality/speed прогрев выполняется отдельно
и не включается в измеряемые запросы; детали записываются в `warmup.jsonl`.

Ollama может повторно использовать KV-кэш общего префикса даже после прогрева.
По возможности сохраняется `prompt_eval_cached_count`; отсутствие этого поля
не означает нулевой кэш. Поэтому не выдавайте TTFT за изолированное время prefill.

## 6. Независимая оценка открытых ответов — желательно для статьи

Самый доступный вариант — слепая человеческая оценка заранее выбранного повтора:

```bash
python research.py export-human --run runs/quality --out runs/human --temperature 0 --repeat 0
```

Получатся `blind_ratings.csv`, `RUBRIC.md` и `PRIVATE_mapping.json`.
В CSV 30 пар с анонимными X/Y. Заполните `rater` (любой псевдоним), `score_x`,
`score_y` (целые 1–10), `winner` (`X`, `Y` или `tie`) и `reason`.
Победитель должен соответствовать баллам. Сначала прочитайте рубрику.
`PRIVATE_mapping.json` до завершения оценки не открывайте и оценщикам не передавайте.
Желательны два независимых оценщика: каждому — отдельная копия исходного CSV.

Одна заполненная таблица:

```bash
python research.py score-human --ratings runs/human/blind_ratings.csv --key runs/human/PRIVATE_mapping.json --out runs/human/summary.json
```

Две заполненные копии:

```bash
python research.py score-human --ratings runs/human/rater1.csv runs/human/rater2.csv --key runs/human/PRIVATE_mapping.json --out runs/human/summary.json
```

Если хотите дополнительно проверить именно LLM-as-a-Judge, установите локально
третью модель **другого семейства** и выполните (замените `ИМЯ_МОДЕЛИ` реальным тегом):

```bash
python research.py judge --run runs/quality --model ИМЯ_МОДЕЛИ --temperature 0 --repeat 0 --context 4096
```

Это ещё **60 запросов**: 30 пар × два порядка ответов. Судья из семейства Llama
или Qwen будет отклонён. Маленький судья не считается достоверным экспертом
автоматически: сравните его с человеческой разметкой. Невалидные JSON/баллы,
противоречивые победители и несогласие после перестановки отмечаются отдельно.
Не выбирайте удобный повтор после просмотра результатов.

## 7. Как продолжить прерванный запуск

Повторите **точно исходную команду** с теми же параметрами и добавьте
`--resume --retry-errors`. Например:

```bash
python research.py run --suite quality --out runs/quality --repeats 3 --temperatures 0 0.7 --context 2048 --budget 384 --resume --retry-errors
```

Готовые успешные запросы пропускаются, ошибки повторяются. История попыток остаётся
в JSONL; анализ берёт последнюю попытку каждого задания. При изменении кода,
моделей, версии Ollama, зависимостей или параметров продолжение блокируется:
создайте новую папку и полноценную новую серию, не объединяйте разные условия.
Не запускайте два процесса в одну папку одновременно.

## 8. Просмотр результатов

```bash
streamlit run streamlit_app.py
```

Откройте адрес из терминала (обычно `http://localhost:8501`). Интерфейс читает
только `runs/*/analysis/summary.json`, показывает coverage и фактические настройки.
Никаких заранее вписанных «80% побед» и автоматических вызовов моделей в нём нет.
Графики для статьи сохраняются одновременно как PNG и векторный PDF.

## 9. Что прислать мне для новой статьи

Нужны целиком папки `runs/quality`, `runs/speed`, `runs/cold`, `runs/human`
(если выполняли оценку), папка `judge_*` (если запускали судью) и `preflight.json`.
Для этого из `LLM_Lab_2` после основных запусков:

```bash
tar -czf results_for_article.tar.gz preflight.json runs
```

`runs` исключён из Git, поэтому обычный push результаты не передаст.
Отправьте архив отдельно. Самые важные файлы: `manifest.json`, `plan.json`,
`dataset.json`, `raw.jsonl`, `gpu.jsonl`, `warmup.jsonl` и папка `analysis`.
Нужны исходные ответы и ошибки, а не только скриншоты красивых диаграмм.

Всего обязательные основные серии: **490 запросов + прогревы** (360 + 120 + 10).
Smoke — ещё 4. Время зависит от оборудования и длины выходов; фиксированное
обещание продолжительности здесь было бы недостоверным.

## 10. Какие величины анализируются

- TTFT: время клиента до первого непустого текстового фрагмента, включая накладные расходы.
- E2E: до завершения потока; дополнительно сохранено время последнего текста.
- Серверное время на токен: `eval_duration / eval_count`, отдельно от клиентского TPOT.
- Клиентский TPOT: оценка по первому/последнему фрагменту и точному числу токенов;
  не выдаётся за прямой замер каждого интервала между токенами.
- Tokens/s и chars/s: токенизаторы различаются, поэтому полезны обе величины.
- BLEU: отдельно sentence BLEU и corpus BLEU по повтору; это разные агрегаты.
- ROUGE-1/L: F1 с Unicode-токенизацией слов; дополнительно вариант по пробелам
  для исследования чувствительности оформления. Морфологическая нормализация не заявляется.
- Objective task success: факты/логика/извлечение/JSON и код при включённом Docker;
  формат и выполнение функции также сохраняются отдельно. Открытые задачи требуют оценки.
- 95% bootstrap-интервалы качества: 2000 выборок по задачам, с усреднением повторов
  внутри задачи; это диагностический набор из 30 задач, а не универсальный рейтинг LLM.

## 11. Краткая схема Overleaf

Это понадобится **после переписывания статьи по полученным данным**:

1. Соберите ZIP с `ivanova-minchuk.tex`, неизменённым `its_conf.sty` и PDF/PNG рисунками,
   указанными в `includegraphics`. Эти файлы должны лежать в корне ZIP.
2. Overleaf → **New project → Existing project (.zip)** (в некоторых версиях Upload Project).
3. Загрузите ZIP и откройте созданный проект.
4. В настройках выберите главный документ `ivanova-minchuk.tex` и компилятор **pdfLaTeX**.
5. Нажмите **Recompile**, проверьте ровно две страницы и скачайте PDF.

Сейчас `ivanova-minchuk.tex` ещё содержит анализ старой серии. Не выдавайте его за
статью по новым экспериментам: обновление будет выполнено после получения архива.
