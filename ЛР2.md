**Лабораторная работа №2**

**Время инференса и сравнение двух языковых моделей**

# **Цель работы**

Целью данной лабораторной работы является практическое сравнение двух языковых моделей по двум независимым направлениям: по скорости работы (метрики времени инференса) и по качеству генерируемых ответов (методы сравнительной оценки LLM). В рамках работы необходимо развернуть две модели одним из предложенных способов, измерить для них метрики производительности, сравнить качество их ответов с помощью методов, применяемых на практике для оценки LLM, и сделать выводы о соотношении скорости и качества у выбранных моделей.

# **Развёртывание моделей для сравнения**

Для выполнения работы необходимо получить доступ к двум языковым моделям, которые будут сравниваться между собой. Ниже описаны несколько вариантов развёртывания — можно выбрать любой из них либо скомбинировать несколько для более полного сравнения.

## **Вариант А. Обе модели — локально через LM Studio**

LM Studio — это приложение с графическим интерфейсом для запуска открытых моделей в формате GGUF на собственном компьютере. Порядок действий:

- Скачать и установить LM Studio с официального сайта lmstudio.ai.
- В разделе поиска моделей загрузить две разные модели для сравнения (например, различающиеся по числу параметров или семейству — Qwen 2.5 7B и LLaMA 3.1 8B, либо две версии одной модели с разной квантованной точностью).
- Во вкладке Developer / Local Server запустить локальный сервер — LM Studio поднимает OpenAI-совместимый REST API, обычно доступный по адресу http://localhost:1234/v1.
- Обращаться к загруженной модели можно теми же средствами, что и к OpenRouter в лабораторной работе №1 — через библиотеку openai, указав base\_url="http://localhost:1234/v1" и произвольный (неиспользуемый) api\_key.

Преимущество этого варианта — полный контроль над окружением и отсутствие сетевых задержек; ограничение — необходимость достаточно мощного оборудования (GPU или объёмная оперативная память) для комфортной работы моделей.

## **Вариант Б. Обе модели — через API**

Второй вариант — обращаться к обеим моделям через облачный API, не разворачивая их локально. Можно использовать сервис OpenRouter, уже применявшийся в лабораторной работе №1 (единый OpenAI-совместимый интерфейс к множеству моделей), либо API-провайдеров, специализирующихся на высокой скорости инференса, например Groq, — это даёт наглядную разницу в throughput по сравнению с моделями, развёрнутыми локально. Такой вариант не требует мощного оборудования, но зависит от сетевого соединения и ограничений (rate limits) выбранного провайдера.

## **Вариант В. Смешанный — одна модель локально, другая через API**

Третий вариант объединяет предыдущие два: одна модель разворачивается локально через LM Studio, а вторая вызывается через API. Такой подход позволяет напрямую сопоставить локальный и облачный инференс — в частности, оценить, насколько сетевые задержки и различие в вычислительных ресурсах влияют на измеряемые метрики времени ответа.

# **Метрики времени инференса**

Для каждой из двух моделей, независимо от способа их развёртывания, необходимо вычислить следующие метрики:

При измерении важно учитывать режим получения ответа: в потоковом режиме (streaming) токены поступают по мере генерации, что позволяет отдельно замерить TTFT и TBT/TPOT; в синхронном режиме (non-streaming) клиент получает весь ответ целиком только после завершения генерации, и напрямую доступна только суммарная задержка (Total Latency).

# **Методы сравнения качества ответов двух LLM**

Помимо скорости, модели необходимо сравнить и по качеству генерируемых ответов. На практике для этого применяются следующие подходы.

## **LLM-as-a-Judge — модель в роли судьи**

Третья («судейская») модель используется для сравнения ответов двух других моделей. Применяются два основных формата:

- Слепой тест (парное сравнение / Arena): модели-судье подаются промпт и оба ответа — Модели А и Модели Б — без указания, какой из них какой модели принадлежит. Судья должен выбрать, какой ответ лучше, и обязательно обосновать свой выбор.
- Абсолютная шкала (score-based): судья оценивает каждый ответ отдельно по шкале, например от 1 до 5 или от 1 до 10, по заданным критериям (полезность, точность, полнота и т. д.).

## **Человеческая оценка (Human-in-the-loop)**

Самый точный, но и самый дорогой способ сравнения — оценка живыми людьми. Обычно для этого используют собственный небольшой инструмент (например, интерфейс на Gradio или Streamlit), в котором аналитики или сам исследователь размечают ответы. Для оценки формируется выборка из 50–100 разнородных промптов, охватывающих разные типы задач: инструкции, творческие запросы, логические задачи, программирование. Асессоры вслепую сравнивают пары ответов и отмечают «Модель 1 лучше», «Модель 2 лучше» или «Ничья» — именно по такому принципу устроена платформа LMSYS Chatbot Arena.

**BLEU и ROUGE подробнее**

BLEU (Bilingual Evaluation Understudy) и ROUGE (Recall-Oriented Understudy for Gisting Evaluation) — классические метрики автоматической оценки текста, изначально разработанные для машинного перевода (BLEU) и суммаризации (ROUGE). Обе метрики сравнивают сгенерированный моделью ответ не с ответом другой модели, а с заранее подготовленным эталонным («золотым») ответом, оценивая совпадение n-грамм — последовательностей из нескольких слов подряд.

- BLEU измеряет точность (precision): какая доля n-грамм сгенерированного ответа встречается в эталоне. Метрика чувствительна к точным формулировкам и штрафует за слишком короткие ответы (brevity penalty).
- ROUGE измеряет в первую очередь полноту (recall): какая доля n-грамм эталона воспроизведена в сгенерированном ответе. Чаще всего используются варианты ROUGE-N (совпадение n-грамм фиксированной длины) и ROUGE-L (по наибольшей общей подпоследовательности слов).

Чтобы сравнить BLEU и ROUGE двух моделей, необходимо для одного и того же набора промптов заранее иметь эталонные ответы, получить ответы обеих моделей на эти промпты, вычислить BLEU и ROUGE каждого ответа относительно соответствующего эталона, а затем сравнить средние значения метрик между моделями. Вычислить обе метрики можно с помощью библиотеки evaluate от Hugging Face либо отдельных пакетов sacrebleu и rouge-score:

pip install evaluate rouge\_score sacrebleu

from evaluate import load

bleu = load("bleu")

rouge = load("rouge")

bleu.compute(predictions=[model\_answer], references=[[reference\_answer]])

rouge.compute(predictions=[model\_answer], references=[reference\_answer])

Важное методологическое ограничение: BLEU и ROUGE осмысленны только там, где для промпта в принципе можно сформулировать один сравнительно устойчивый эталонный ответ — например, для суммаризации, перевода, ответа по документу в RAG или фактологического вопроса. Для открытых творческих или диалоговых промптов, где хороших формулировок ответа может быть множество, эти метрики дают ненадёжную картину и должны использоваться вместе с LLM-as-a-Judge или человеческой оценкой, а не вместо них.

# **Дополнительные метрики и инструменты оценки**

Наряду с методами прямого попарного сравнения, для оценки качества LLM используется более широкий набор метрик и инструментов.

- Автоматические метрики (BLEU, ROUGE): работают быстро и дёшево, но плохо улавливают смысл ответа, когда правильных формулировок может быть несколько.
- Оценка людьми: остаётся золотым стандартом качества, однако медленная, дорогая и плохо масштабируется — по сути, это развёрнутая версия Human-in-the-loop, описанного выше.
- LLM-как-судья: быстрый способ, близкий по результатам к человеческой оценке, но подверженный системным искажениям — на оценку влияют длина ответа, порядок показа вариантов и смещение судьи к «своему» стилю.
